## 개발 JavaScript 압축, 왜 매번 손이 멈추는가

개발 JavaScript 압축은 프론트엔드 작업에서 가장 마지막에, 가장 귀찮게 남는 단계입니다. 코드를 다 짜고 배포 직전에 파일 크기를 확인하면 예상보다 몇 배는 큰 숫자가 찍혀 있고, 그때부터 빌드 설정 파일을 뒤지기 시작합니다. 터미널에서 `npm run build`가 실패하면 에러 로그는 수십 줄이고, 원인은 대개 설정 한 줄입니다.

문제는 압축 자체가 어려운 게 아니라는 점입니다. 어려운 건 "환경"입니다. Node 버전, 번들러 버전, 플러그인 호환성, ESM과 CJS 혼용 문제까지 겹치면 코드 한 줄 안 바꿨는데 반나절이 사라집니다.

## 원인: 빌드 도구에 너무 많은 것을 얹었기 때문

2026년 기준으로 프론트엔드 빌드 환경은 더 파편화됐습니다. Vite, esbuild, Turbopack, Rollup, webpack이 각자 다른 설정 문법을 쓰고, 같은 플러그인이라도 메이저 버전이 다르면 옵션 이름이 달라집니다. 여기에 TypeScript 컴파일, 트리 셰이킹, 폴리필 주입까지 한 번에 처리하려다 보니 설정 파일이 수백 줄로 불어납니다.

정작 필요한 건 "내가 쓴 JS 파일의 용량을 줄이는 것" 하나인데, 그걸 위해 빌드 파이프라인 전체를 세팅하고 있는 셈입니다.

### 기능 상세

핵심은 세 가지입니다. 첫째, 파일을 끌어다 놓거나 코드를 붙여넣으면 즉시 압축이 실행됩니다. 공백, 주석, 줄바꿈을 제거하고 불필요한 문자를 정리해 결과물을 내놓습니다. 둘째, 압축 전후 용량과 절감률을 숫자로 확인할 수 있어 "몇 퍼센트 줄었는지"를 감으로 판단하지 않아도 됩니다. 셋째, 변수명 단축까지 포함한 경량화가 적용되어 단순 공백 제거보다 더 작은 결과를 얻을 수 있습니다.

여기에 더해 HTML, CSS, JSON, 이미지 압축 도구가 같은 사이트에 모여 있어 배포 전 정리 작업을 한 곳에서 처리할 수 있습니다. 빌드 설정을 건드리지 않고 결과물만 손보고 싶을 때 특히 유용합니다.

## 실제로 써본 순서

테스트용으로 약 240KB짜리 유틸리티 스크립트 묶음을 넣어봤습니다. 파일 선택 후 처리까지 걸린 시간은 2초 안쪽이었고, 결과물은 90KB대까지 줄었습니다. 체감상 절반 이상이 사라진 셈입니다. 압축된 코드를 다시 에디터에 붙여 실행해보니 동작은 원본과 동일했습니다.

주의할 점도 확인했습니다. 세미콜론을 생략한 코드는 압축 후 예상과 다르게 묶일 수 있으므로, 원본은 반드시 따로 백업해 두는 편이 좋습니다. 또한 디버깅이 필요한 개발 중에는 압축본을 쓰지 말고, 배포 직전 단계에서만 적용하는 것이 안전합니다.

빌드 환경을 새로 세팅하는 데 드는 시간을 생각하면, 단발성으로 파일 몇 개를 정리할 때는 이쪽이 훨씬 빠릅니다. 반대로 매 커밋마다 자동화가 필요한 팀 단위 작업이라면 기존 번들러 파이프라인에 압축 플러그인을 붙이는 편이 맞습니다. 상황에 따라 도구를 나눠 쓰는 게 결국 시간을 아끼는 방법입니다.
